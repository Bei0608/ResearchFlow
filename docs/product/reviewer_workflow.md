# 评审人的完整操作流程

## 目标角色

- **评审人**：查看案例、保存草稿、修改并提交人工评分；
- **项目所有者**：配置评测集/量表、发起运行、查看统计并生成报告；
- V1.1 允许同一演示用户兼任两种角色，但数据库和 API 保留角色边界。

## 前置条件

项目必须提供可公开分发的演示用户、Agent 版本、评测集、候选回答、程序指标和
量表种子数据。评审人不需要准备模型密钥或本地 PDF，就能完成以下人工流程。

启动服务后执行以下幂等命令即可准备完整流程；密码仅在首次创建账号时使用：

```powershell
$env:RESEARCHFLOW_DEMO_PASSWORD = "至少8位演示密码"
python -m scripts.bootstrap_demo_platform --username researchflow-demo
Remove-Item Env:RESEARCHFLOW_DEMO_PASSWORD
```

## A. 项目所有者准备评审

1. 登录并进入默认 Workspace；
2. 选择演示 Agent 应用及一个不可变 Agent 版本；
3. 选择已发布的评测集版本和量表版本；
4. 创建 Evaluation Run，系统生成逐案例候选输出；
5. 程序 Evaluator 生成独立的 program metrics；
6. 将运行状态标记为 `READY_FOR_REVIEW`；
7. 创建 Review Task 并指定评审人；
8. 在任务摘要中核对案例总数、待评审数、失败案例数和程序评分状态。

V1.1 演示数据可以直接导入一份已完成运行，以便没有模型密钥时仍能评审。真实
模型运行是另一条入口，但两者在数据结构上使用相同的 Evaluation Run。

## B. 评审人执行评审

### 1. 打开任务

评审人登录后进入“我的评审任务”，页面必须显示：

- 任务名称、评测集版本、Agent 版本；
- 总案例数、已提交数、草稿数、待处理数；
- 是否允许修改已提交评审；
- 量表名称和版本。

### 2. 查看单个案例

案例页同时展示但明确分区：

- 输入问题及期望路由；
- Agent 实际回答；
- 检索证据、引用、来源和页码；
- 工具/工作流摘要；
- 程序评分区，标记为“程序结果，仅供参考”；
- 人工量表区，尚未评分时不得显示伪造默认分。

### 3. 保存草稿

评审人可填写部分维度、总评和评论后点击“保存草稿”。系统需要：

- 保存当前字段和 `status=DRAFT`；
- 记录 reviewer、rubric version、revision、保存时间；
- 返回明确成功提示；
- 重载页面仍显示已保存内容；
- 草稿不进入正式分数统计，只进入进度统计。

### 4. 修改草稿

评审人重新打开草稿，修改评分或评论并保存。系统不得直接丢失历史：至少保存
当前 revision，审计事件记录修改；正式提交后若允许纠错，则必须产生新 revision。

### 5. 提交评审

点击提交时系统校验所有必填维度和评论规则。成功后：

- 状态变为 `SUBMITTED`；
- 记录提交时间；
- 该修订进入人工评分统计；
- 默认界面变为只读；
- 若需纠错，执行“创建修订”，不能覆盖原提交。

### 6. 切换案例并完成任务

评审人可使用“上一条/下一条”和状态筛选继续处理。所有案例提交后，Review Task
状态变为 `COMPLETED`；存在草稿时不能伪装为完成。

## C. 修改已提交评分

V1.1 建议采用“允许评审人自行纠错，但完整留痕”：

1. 点击“创建修订”；
2. 系统复制上一已提交版本为新草稿，revision 加一；
3. 修改并再次提交；
4. 统计只使用最新有效提交；
5. 报告注明存在修订，并可查看旧版本；
6. 审计记录修改人、时间和可选修改原因。

不采用直接 UPDATE 覆盖，因为这会破坏可审计性。

## D. 查看统计

项目所有者在运行统计页查看：

- 任务完成率、草稿数、已提交数；
- 各人工评分维度的均值、分布和通过率；
- 各程序指标的均值/通过率；
- 程序与人工结果并列展示，不默认合并；
- 失败案例列表；
- Candidate 相对 Baseline 的变化和 Gate 结论。

统计必须标注样本数和缺失数，避免少量已提交评分被误解为全量结论。

## E. 生成报告

项目所有者点击“生成报告”，输出：

- `report.json`：机器可读、供 CI 或二次分析；
- `report.html`：评审人和面试演示可直接查看。

报告必须包含：运行身份、Git Commit、Agent/数据集/量表版本、配置快照、程序指标、
人工指标、样本数、未完成数量、失败案例、Baseline 对比、Gate 结论和生成时间。
人工评分区必须显示 reviewer 数量和 rubric version；程序评分区必须显示 evaluator
及版本。

## F. 异常和恢复

| 场景 | 预期行为 |
|---|---|
| 保存时网络中断 | 页面保留输入，允许再次提交相同幂等键 |
| 重复点击保存 | 不产生重复 revision |
| 提交缺少必填项 | 返回字段级错误，保持草稿 |
| 运行中某案例失败 | 保留错误结果，可人工标记“不可评审” |
| 其他用户访问任务 | 返回 403/404，且不泄露资源是否存在 |
| 报告生成失败 | 不改变评审结果，记录失败并可重试 |
| 程序评分缺失 | 仍允许人工评审，报告明确标记缺失 |

## 最小演示脚本

验收演示控制在 8–12 分钟：登录 → 打开任务 → 评审一例 → 保存 → 重开 → 修改 →
提交 → 查看统计 → 生成报告 → 展示程序/人工分离 → 展示另一用户越权失败。
